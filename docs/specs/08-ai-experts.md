# Модуль «AI-эксперты» — Фаза 2 (черновая спека)

Источник: п. 3.8 и 3.11 исходного ТЗ.

Изолированный AI-сервис — прокси к внешнему LLM API, полностью отключаемый (3.11.9). Не влияет на работу остальных модулей, если выключен/недоступен.

Открытые вопросы перед стартом спринта:
- Какой LLM-провайдер и через какой API — фиксируется отдельно, до спринта, не решается Клод Кодом на лету (ключи/квоты — вопрос владельца проекта)

**Контекст — решено, скоуп раздельный по типу данных:**
- **Кодекс (персонажи, локации)** — на уровне **всей серии** (`PROJECT`), не только текущей книги. Это прямое следствие того, что Кодекс и так общий на всю серию (`CODEXENTRY.project_id`, см. `../data-model.md`) — ассистент должен знать персонажа, даже если он в последний раз фигурировал в другой книге той же серии.
- **Текст рукописи (сцены/главы, которые ассистент читает, чтобы ответить)** — на уровне **только текущей книги** (`BOOK`), не всей серии. Ассистент не подмешивает в контекст сцены из других книг серии — у них может быть свой, ещё не проявленный в этой книге сюжет, и это не то, что должно "протекать" в ответы по текущей книге.
- Практическое следствие для реализации: при сборке промпта — Кодекс тянется по `project_id` текущей книги, а сцены/главы — по `book_id`, а не оба по `project_id`. Это разные запросы к БД, не один общий.
- **Весь текст книги в промпт, не RAG — решено.** Контекст-основа для любого запроса ассистента = полный текст текущей книги (все главы/сцены по `book_id`) + весь Кодекс серии, а не релевантная выборка. Это осознанный выбор простоты для Фазы 2: RAG (эмбеддинги, поиск релевантных фрагментов) добавляет отдельную инфраструктуру и риск того, что ассистент упустит важный, но "непохожий" по векторному поиску фрагмент — для художественного текста, где важны интонация и сквозные детали, это не приемлемый компромисс на старте. Ограничение по лимитам контекста у очень длинных книг (сотни тысяч слов) — известный риск, но обрабатывается отдельно (обрезка/суммаризация как запасной механизм, если/когда конкретная книга в это упрётся), не меняет базовый принцип "по умолчанию — вся книга".

## Масштаб конкретного запроса — отдельное от контекста измерение
Контекст (что ассистент **знает**, п. выше) и масштаб запроса (на какую часть текста нацелено **конкретное действие**, например "предложи вариант сцены") — два независимых понятия, не путать. Ассистент всегда видит всю книгу, но конкретный запрос может быть нацелен уже:
- **Сцена** — весь текст текущей развёрнутой сцены (см. `design/mockup/UI-SPEC.md`, «Редактор — единый текст книги»). Значение по умолчанию.
- **Глава** — все сцены текущей главы.
- **Диалог** — конкретный диалоговый фрагмент внутри сцены (распознавание диалоговых блоков в тексте — деталь реализации этого спринта, не описана здесь отдельно).
- **Выделенный фрагмент** — то, что пользователь выделил в тексте мышью прямо сейчас. При выделении текста в редакторе масштаб запроса переключается на «Выделение» автоматически (см. мокап — выдели фразу в теле сцены, селектор в правой панели переключится сам).

Переключатель масштаба — в правой AI-панели (`.ai-scope-row` в мокапе), под чипами ролей, над типовыми запросами. Влияет только на то, какой фрагмент передаётся как "предмет запроса" в промпте — контекст (вся книга + Кодекс серии) при этом не меняется.
