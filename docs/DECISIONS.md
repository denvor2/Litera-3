## 22.07.2026 Спринт 1 — Рукопись

### Вопрос: Структура проекта (frontend/backend разделение)
**Решение:** Создана структура `frontend/` и `backend/` как отдельные npm-проекты, каждый со своим package.json, tsconfig и структурой.

**Почему:** Позволяет каждому приложению иметь независимые зависимости, версионирование и сборку. Соответствует стандартной практике монорепозиториев.

### Вопрос: Структура Prisma схемы
**Решение:** Все таблицы из Фазы 0 реализованы в Prisma schema, включая модель для VERSION (версионирование сцен).

**Почему:** Спека требует версионирования при переходе статуса сцены. Лучше подготовить схему сейчас, чем мигрировать потом.

### Вопрос: Формат хранения body сцены в БД
**Решение:** TipTap JSON (как указано в спеке) хранится как JSON тип в PostgreSQL.

**Почему:** Позволяет парсить упоминания сущностей и сохранять структуру текста для потенциального экспорта в будущем.

### Вопрос: Дебаунс-задержка для автосохранения
**Решение:** 2 секунды (как указано в спеке 01-manuscript.md).

**Почему:** Прямое соответствие спеке: "Дебаунс 2 секунды после последнего изменения текста".

### Вопрос: Инициализация проекта по умолчанию
**Решение:** При первом запуске фронтенда, если нет проектов, создается проект "Моя рукопись" с книгой по умолчанию.

**Почему:** Упрощает UX для первого пользователя — не нужно вручную создавать проект перед началом работы. Это минимальная инициализация, позволяющая сразу начать писать.

## 22.07.2026 Спринт 2 — Кодекс

### Вопрос: Локализация Кодекса в UI
**Решение:** Кодекс реализован как боковая панель, открываемая кнопкой из режима редактирования сцены. Панель остаётся видимой параллельно с редактором до явного закрытия.

**Почему:** Соответствует спеке (п. 3.4: "доступ из сайдбара при письме"). Боковая панель позволяет быстро проверить/отредактировать сущности не выходя из текста.

### Вопрос: Структура данных для attributes
**Решение:** CodexEntry.attributes хранит динамический JSON с ключами (appearance, personality, goal_conflict для персонажей; description для локаций).

**Почему:** Гибкость для Фазы 2 - новые типы сущностей добавляются без миграции БД, только добавлением новых ключей в form.

## 22.07.2026 Спринт 3 — Экспорт

### Вопрос: Генерация .docx синхронно или асинхронно
**Решение:** Синхронная генерация на backend, блокирующий вызов.

**Почему:** Спека (п. 8.2.1) указывает на синхронную генерацию для разумных объёмов. Асинхронные очереди - Фаза 2, когда книги вырастут на сотни тысяч слов.

### Вопрос: Какие сцены включаются в экспорт
**Решение:** Только сцены со статусом DRAFT и EDITING (исключаются DONE).

**Почему:** Прямо из спеки (п. 3.9.1): это экспорт черновика для чтения, не публикационная выгрузка.

## 22.07.2026 Спринт 4 — Поиск и версии (Фаза 1)

### Вопрос: Где размещать поиск в интерфейсе
**Решение:** Глобальная строка поиска в хедере App, над главным редактором.

**Почему:** Дает доступ ко всему проекту из любого места, типичный паттерн для приложений.

### Вопрос: Как реализовать полнотекстовый поиск без специализированной БД
**Решение:** Простой текстовый поиск в памяти (JavaScript) + поиск по индексам (SQL LIKE).

**Почему:** MVP не требует async индексирования. Для больших проектов - специальная БД (Elasticsearch, Meilisearch) в Фазе 2.

## 22.07.2026 Спринт 5 — UI/UX полировка (Фаза 1)

### Вопрос: Светлая/тёмная тема - сколько вариантов
**Решение:** Две темы (light/dark) с системной автодетекцией и localStorage.

**Почему:** Достаточно для MVP. Кастомные темы - Фаза 2. Автодетекция улучшает UX первого запуска.

### Вопрос: Где хранить настройки пользователя
**Решение:** localStorage для клиента + диалог Settings без backend.

**Почему:** MVP не требует персистентных аккаунтов. Backend для пользовательских настроек - Фаза 3.
